# 软件工程近三年研究现状、能力边界与前沿地图

分析日期：2026-09-21；标题统计截止：2026-09-20

[报告目录](../README.md) · [代表论文与证据边界](evidence/representative-papers.md) · [会议、期刊与统计范围](evidence/venue-sources.md)

## 阅读起点：什么是研究，软工研究什么

**研究，是针对一个尚未充分回答的问题，通过系统的探究，形成有依据、可供他人检查和讨论的认识。** 提出新结构或新方法并验证性能提升，只是其中一种；发现现象、解释原因、建立预测、确定边界，以及检验和修正已有认识，也可以成为研究。

例如，假设“给服务增加缓存，响应反而变慢”尚未得到充分解释，可以研究哪些环境、负载和缓存设计会出现这种现象、原因是什么，也可以研究怎样更可靠地分析这类问题。前者贡献对现象和机制的认识，后者贡献分析方法；不必都以提出更快的缓存策略收尾。

判断一项研究是否形成完整结果，需要同时看**结论是否有证据支持、适用边界是否清楚，以及相较已有认识增加了什么有价值的内容**。问题重要，不自动意味着所得结论有价值；需要说明它澄清了什么未知、修正了什么认识或确定了什么边界。实证分析不必超过某个 baseline 或达到固定样本量，可靠地确认或限制已有结论也可能有价值。[研究方法与评价依据](evidence/venue-sources.md#research-methods)

软件工程研究整个软件生命周期中的**人、开发过程、代码/测试/文档等产物、工具和运行系统**。把一个项目做出来、修好一个缺陷有工程价值；研究还需要提炼出问题，并形成可检查的新方法或认识。以 LLM 自动修复代码为例：

| 研究做法 | 可以回答的问题 |
| --- | --- |
| 提出方法或工具 | 能否利用代码依赖关系，为修复 Agent 选择更合适的上下文，减少错误修改？ |
| 做实证分析 | 修复失败常发生在哪一步，与任务或项目的哪些特点有关？ |
| 研究开发者与流程 | 使用修复助手后，开发者验证补丁的时间和漏掉的错误怎样变化？ |
| 建立评测或验证方法 | 测试通过的补丁是否真的正确，怎样识别只碰巧通过已有测试的错误补丁？ |

这些研究与系统领域都可以采用“发现问题—提出解释或方法—用证据检验”的路径；软工还研究人的行为和协作过程，结果也可能体现为正确性、可维护性或开发者工作量的变化。阅读后面的研究地图时，除了看研究对象，还要追问：**作者增加了什么认识或能力，用什么证据支持？**

## 先说结论

软件工程近三年的主线不是简单的“大家开始用大语言模型（LLM）写代码”，而是研究对象和研究方法同时发生了变化：

1. **2024 年主要把 LLM 当作一种新的开发工具**：研究代码生成、测试生成、程序修复、解释和开发者体验，典型问题是“它能不能完成一个具体任务”。
2. **2025 年开始把 LLM 当作能够操作仓库和工具的智能体（Agent）**。这里的 Agent 不只是回答一次问题，而是会自己查找文件、调用工具、运行测试，再根据结果继续行动。研究问题因此从生成一个函数，转向解决真实问题单（issue）、修改多个文件和反复验证；与此同时，评测题目可能被模型提前见过、实验成本高、结果难复现等问题也集中暴露出来。
3. **2026 年的前沿正在转向 Agent 工程本身**：把 Agent 当作一种需要开发和维护的软件系统，研究怎样看清它每一步做了什么、为何失败，怎样测试长时间任务、限制危险操作、管理上下文和度量成本，并把代码分析、测试、数学约束和运行反馈放进它的工作循环。
4. **测试、分析、调试、安全、维护并没有过时**。它们仍是软工研究的主体，LLM/Agent 则成为新的被测对象或自动化工具。只调整提示词（prompt）、在旧题上报告分数提升，往往不足以说明研究价值；更有说服力的工作会检查真实代码、执行结果，以及程序分析或测试究竟改善了什么。
5. **理解当前前沿，不能只看“Agent 会不会写代码”**。更关键的问题是：它能否稳定完成真实工程任务，过程是否可观察，评测是否可信，代码分析能否给它提供可靠事实，模型、工具和插件是否安全，以及它怎样与开发者协作、怎样进入生产运维。

读完这份报告，希望建立的不是一张“我应该选哪个题”的清单，而是四层认识：**软工研究覆盖哪些问题、近三年哪些方向发生了变化、各方向目前实际做到什么程度，以及下一步前沿为什么会这样发展。**

### 阅读约定：几个反复出现的词

本文中的 Agent 特指以 LLM 决定或执行多步工具操作的程序；传统脚本、调度算法或名为 agent 的后台进程不自动计入。技术路线首次出现时说明具体任务和主要做法，之后沿用简称。模型具体型号或规模未由证据确认时，不从“AI”“Agent”名称推断。

| 术语 | 可以先怎样理解 |
|---|---|
| LLM | 能读写自然语言和代码的大语言模型，例如 ChatGPT 背后的模型 |
| Agent | 能围绕目标连续执行多步操作的程序，例如“读问题单→搜索代码→修改→运行测试→继续修正” |
| Agentware | 由 LLM Agent 驱动的软件系统，包括模型调用、提示词、工具和运行流程；它是软件工程的研究对象，不是另一种基础模型 |
| 评测集（benchmark） | 一套共同使用的任务和判定规则，用来比较方法；是否公平还取决于数据、环境和实验设置 |
| 对照方法（baseline） | 新方法需要比较的已有方法，相当于实验中的参照组 |
| 复现实验材料（artifact） | 论文附带的代码、数据、配置和运行说明，供别人重复实验 |
| 实证研究（empirical study） | 系统收集真实数据，通过统计、访谈或案例分析总结规律，而不一定提出新算法 |
| 仓库级任务（repository-level task） | 不只改一个函数，而是要理解并修改一个真实代码仓库中的多个文件、依赖和测试 |
| 执行轨迹（trajectory/trace） | 程序或 Agent 从开始到结束经历的一连串状态、动作和结果 |
| 消融实验（ablation） | 去掉方法中的一个部件重新实验，判断该部件是否真的有用 |
| 判定标准（oracle） | 用来判断结果是否正确的依据，例如测试是否通过、输出是否符合规格 |
| 分类体系（taxonomy） | 把大量现象按清楚的规则分门别类，例如把失败分为定位错误、工具错误和环境错误 |
| 安全护栏（guardrail） | 限制危险行为的检查和权限规则，例如禁止 Agent 未经批准删除生产数据 |
| 规格（specification） | 对软件应做什么、必须满足什么约束的明确描述，可以是自然语言、接口定义或可执行检查 |
| 闭环 | 执行动作后检查真实结果，再依据反馈决定下一步，例如修复后运行测试，失败则继续定位 |
| token | 模型切分和处理文本的计量单位；调用成本不仅取决于调用次数，也取决于输入、输出和重复读取的 token 数 |

## 2. 先建立一张软工研究地图

**软件工程研究如何在现实约束下，持续构建和演化有用、可信、易于维护的软件，以及支撑这一目标的开发过程、协作方式、工具和方法。** 

这里的现实约束包括需求不断变化、时间与资源有限，以及多人协作。

**软件本身需要达到什么要求：**

- **有用、符合需求**：解决真实问题，行为符合使用者的需要；一个从不崩溃、却实现了错误需求的系统，仍然没有达到目标。
- **质量可信**：根据使用场景满足正确性、可靠性、安全、性能等要求，并有依据判断是否满足；“健壮、可靠”是重要目标，但不是全部。
- **能够持续变化**：需求、依赖和运行环境变化后，仍然容易理解、修改和验证，避免每次改动都付出巨大代价。

**开发、运行和维护过程需要做到什么：**

- **让团队持续协作**：支持分工、沟通、验证、交接和维护，减少对少数熟悉全部细节的个人的依赖。
- **用过程、工具和方法支撑质量**：帮助开发者理解复杂软件、减少错误、管理变更，并在运行中发现故障、诊断和恢复。
- **控制成本与风险**：合理使用时间、人力和计算资源，理解质量、交付速度与维护负担之间的权衡，例如更多检查可能增加交付成本，更快上线也可能留下长期维护负担。

这些目标会相互影响，具体研究需要说明在什么条件下改善了什么、付出了什么代价，并提供可信证据，而不是要求所有指标同时达到最高。

下面按研究对象和问题划分软件工程的主要板块；每个板块都可以采用前文介绍的方法、实证分析或评测研究。

| 研究板块                                  | 它真正关心的问题                                                       | 常见证据                                                    |
| ------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------- |
| 测试、调试与程序分析                            | 怎样发现、定位、复现、解释和修复缺陷。“测试”主动运行用例找错，“调试”追查错误原因，“程序分析”系统检查代码结构或运行行为 | 覆盖率（测试执行了哪些代码）、真实缺陷、不运行程序的静态分析、运行程序后收集信息的动态分析、主动制造故障的实验 |
| 安全与隐私                                 | 软件、依赖和生成代码如何引入漏洞，怎样检测和缓解                                       | 已公开漏洞编号（CVE）、攻击实验、恶意软件包、真实漏洞修复、误报和漏报                    |
| 维护与演化                                 | 软件使用多年、不断升级依赖和更换团队时，怎样让它仍然容易理解和修改                              | 代码提交记录、问题单、API 变化、重构（保持外部行为、调整内部结构）、长期积累的维护成本（技术债）      |
| 开发者与组织                                | 工具怎样改变人的效率、理解过程、协作和责任                                          | 用户研究、访谈、实验、真实使用记录、长期部署                                  |
| 需求、设计与架构                              | 怎样把用户想法变成可以检查的要求，并让大型系统的模块划分保持合理                               | 需求文档、架构决策、需求到代码的对应关系、性能和可靠性等质量要求                        |
| DevOps、云与可靠性                          | 软件上线后，怎样自动发布、持续监控、诊断故障并尽快恢复                                    | 日志、告警、生产故障、持续集成与发布（CI/CD）、服务调用链、可用性等服务目标                |
| AI for SE（用 AI 做软工）                   | 用机器学习、LLM 或 Agent 改进测试、修复、维护等任务                                | 模型输出、真实的正确性判据、工具执行结果和开发者评价                              |
| SE for AI（为 AI 做软工，本文侧重 LLM Agent 工程） | 把学习系统或 Agent 应用当作软件，研究怎样开发、测试、维护和管理它；Agentware 是其中一种对象         | 执行轨迹、工具调用、提示词与配置、模型版本、运行时安全护栏                           |

这些板块是问题领域，不是论文贡献本身。具体工作还需要说明发现、方法或评测相较已有研究增加了什么；数据集、分类体系和复现实验材料也可以支持他人继续研究。

## 3. 三年变化：从助手到 Agent，再到 Agent 工程

### 3.1 可量化的方向信号

下面是对所选主会论文标题的多标签关键词统计：

| 标题信号                |  2024 |  2025 | 2026* | 应怎样理解                               |
| ------------------- | ----: | ----: | ----: | ----------------------------------- |
| LLM / 生成式 AI        |  8.2% | 19.2% | 20.7% | 2025 年发生跃迁，2026 年保持高位但问题开始深化        |
| 明确的 Agent / Agent 化 |  0.4% |  3.8% |  7.7% | 标题占比明显上升；基数小且年度样本不同，不能换算成全领域论文数量的增幅 |
| 测试、调试、修复、验证、分析      | 24.5% | 27.6% | 25.4% | 始终约占四分之一，传统核心方向非常稳定                 |
| 安全与隐私               |  4.5% |  5.1% |  6.4% | 稳定上升，并与生成代码、依赖和 Agent 安全交叉          |
| 供应链、依赖、包和库          |  5.5% |  5.3% |  6.0% | 不是爆发热点，但保持稳定且工程价值高                  |
| 能耗、绿色与可持续           |  0.2% |  0.6% |  0.8% | 规模仍小，属于值得观察而非已经成熟的方向                |

\* 2026 只统计 ICSE 和 FSE，不能与包含 ASE 的前两年做严格总量比较。

在这组标题样本中，**明确提到 Agent 的标题占比增长，比泛 LLM 标题更明显**；测试与分析相关标题也始终占较大比例。结合代表工作，可以看到一种常见组合：Agent 负责规划、生成和工具调用，程序分析、测试及权限检查为它提供有适用范围的代码证据、正确性判据和操作约束。

### 3.2 2024：AI 编程助手与单任务能力

2024 年的典型问题是：Copilot/ChatGPT 对代码生成、摘要、日志、程序修复、测试生成和开发者理解到底有没有帮助？研究形态多为一个具体任务、一个模型调用策略和一个既有数据集。

这一阶段有两个重要认识：

- **可用性不等于模型准确率。** ICSE 2024 的[开发者调查](evidence/representative-papers.md#assistant-usability)覆盖 410 名开发者，发现他们看重 AI 助手减少按键、加快任务和帮助回忆语法，但也因需求未满足、输出难控制而不采用建议。这把评价对象从生成代码本身扩展到人怎样验证和修正建议；调查不能单独证明长期团队生产力提升。
- **LLM 与经典方法结合。** [ClarifyGPT](evidence/representative-papers.md#clarifygpt)先检查自然语言需求的歧义，再向用户提问并生成代码；[AutoSD](evidence/representative-papers.md#autosd)让代码修复 LLM 提出假设，执行调试器命令，用真实返回结果修正判断。AutoSD 于 2024 年在线发表、归入 2025 年期刊卷；这里按在线日期观察这种工具反馈方法，不把它写成某年才首次出现的机制。

这一时期最容易复制、也最容易迅速过时的是：“选一个传统任务，换成 ChatGPT，再与旧模型比较”。如果没有新问题、真实场景、强基线和失败分析，现在已经很难构成有力贡献。

### 3.3 2025：仓库级任务、Agent 化和评测是否可信

2025 年研究对象明显从代码片段走向仓库级任务：例如根据一个真实问题单，在多个文件中找到原因、修改代码、处理 API 变化、复现失败并完成修复。Agent 能够搜索仓库、运行命令、观察结果并继续行动，但社区也开始追问：复杂的 Agent 真的比简单、固定的工作流程更好吗？

三个变化尤其重要：

1. **简单流程成为重要的对照方法。** FSE 2025 的 [Agentless](evidence/representative-papers.md#agentless)用“定位—修复—验证”三个固定阶段，不让模型自由规划复杂步骤，在当时 SWE-bench Lite 仓库缺陷修复评测上取得有竞争力的结果和成本。加入多个 Agent、反思或记忆的工作，需要与这类流程比较，并用消融实验说明新增组件的价值；它不证明所有任务都应使用固定流程。
2. **评测集是否可信成为研究问题。** [Unseen Horizons](evidence/representative-papers.md#unseen-horizons)在保留功能和输出的目标下改写代码、描述与依赖上下文，再检查 LLM 代码生成的测试通过率，结果明显下降。这提示成绩可能受训练数据暴露和对熟悉表述的依赖影响，不能仅凭下降幅度判定全部差距都来自“记住答案”。评测需要检查时间划分、重复数据、真实依赖和多次运行成本，而不能只看前 k 个候选中至少一个通过的比例（pass@k）。
3. **Agent 自身成为被研究的软件。** ASE 2025 的[轨迹研究](evidence/representative-papers.md#agent-trajectories)统一修复 Agent 的模型分析文本、工具动作和返回结果，比较成功与失败过程。[Watson](evidence/representative-papers.md#watson)研究“认知可观测性”：通过提示词归因等方法推断并检查哪些输入信息影响了决策，而非直接读出模型真实的内部推理。另有 [Agent 框架缺陷研究](evidence/representative-papers.md#framework-bugs)从 LangChain、LlamaIndex、Haystack 的真实 PR 中抽取 1,026 个缺陷；该论文属于 Industry Showcase，仅作补充证据，不计入 Research Track 标题统计。

同年也出现了更贴近生产的问题。[Triangle](evidence/representative-papers.md#triangle)用多个角色的 LLM Agent 处理云服务故障分诊，根据故障信息判断责任团队，并协调分散在不同团队中的知识。它在真实云环境中报告分诊准确率和接手时间的改善，展示了特定运维环节的价值；这不等于已经验证自主恢复所有生产故障。

### 3.4 2026：把 Agent 当作软件，并建立可验证的工作循环

2026 年 Agent 不再只是论文标题里的解决方案，而成为一种需要专门工程方法的软件形态，有些论文把它称为 Agentware。代表问题包括：

- 怎样观察长轨迹中的思考、动作和工具返回；
- 怎样区分模型能力不足、上下文错误、定位失败、工具失败和工作流设计错误；
- 怎样保证同一任务在模型版本变化后仍可复现；
- 怎样限制 Agent 生成不安全代码或执行危险操作；
- 怎样用代码分析、测试、知识图谱、可由数学或逻辑检查的约束，以及真实运行反馈，给 Agent 提供可靠的外部事实。例如，先用调用图指出某函数会影响哪些服务，再让 Agent 制定修改计划，而不是让它只凭文字猜测。

几项代表工作体现了这种变化：

- [自动修复系统横向分析](evidence/representative-papers.md#bug-fixing-analysis)在 SWE-bench Verified 上比较六种修复系统，不只看最终成功率，还检查文件/代码符号定位和缺陷复现，指出底座 LLM 能力与 Agent 执行流程都需要改进。
- [RefAgent](evidence/representative-papers.md#refagent)把 Java 代码重构分给规划、执行、测试和迭代改进等角色，在八个开源 Java 项目上与单 Agent、搜索式工具和历史人工重构比较，并检查各角色的贡献。
- [SAINT](evidence/representative-papers.md#saint)分析 Java 企业应用，提取服务端点（可调用的 API 入口）信息及端点调用的先后约束，再让 LLM Agent 生成接口测试和可执行业务场景测试。这里“模型”指代码分析形成的端点表示和依赖图，不能与作为生成工具的 LLM 混为一谈。
- [thea](evidence/representative-papers.md#secure-executions)在 Llama 3.1 的代码生成推理中识别并干预与漏洞生成有关的内部表示，在 CyberSecEval 上评测安全性；这是对代码生成模型执行过程的干预，不是给代码审查流程增加一个 Agent。
- [商业 LLM 研究的复现分析](evidence/representative-papers.md#commercial-llm-reproducibility)检查 ICSE 2024 和 ASE 2024 的 86 项研究，并尝试复现其中提供材料、使用 OpenAI 模型的 18 项；只有 5 项具备实际复现条件，其中 2 项部分复现、3 项未复现，没有完整复现的案例。这个结论限于所检查的样本与复现条件，说明模型、环境和材料版本应纳入研究设计。

因此，2026 年值得做的不是给旧任务再包一层 Agent，而是研究 Agent 怎样成为**可测试、可诊断、可约束、可维护、可比较**的工程系统。

## 4. Agent 与软件工程的两条路线

“Agent + 软件工程”至少包含两条相反但互补的路线，理解相关论文时必须分清。

### 4.1 用 Agent 解决软件工程问题（Agent for SE）

通俗地说，这条路线把 Agent 当作工具：原来由开发者完成的查错、改代码、升级依赖或处理告警等任务，现在尝试让 Agent 完成全部或一部分。

典型任务包括：

- 问题单定位与自动修复；
- 测试、模糊测试工具（自动生成大量正常或异常输入）和缺陷复现；
- 代码审查、漏洞检测与依赖升级；
- 代码重构、跨版本/API 迁移、文档更新，以及检查需求是否被代码和测试覆盖；
- 日志分析、告警合并、生产故障分诊和辅助值班人员；
- 规格生成、形式化验证辅助与证明生成。形式化验证是把要求写成严格的数学或逻辑规则，再检查程序是否一定遵守这些规则。

这个方向已经很热，新的工作至少应满足一项：任务过去确实难以自动化；需要多步工具交互；拥有真实工程环境；能提供有竞争力的非 Agent 对照方法；或者能解释 Agent 成功与失败的原因。仅把“规划者、编码者、测试者”三个角色接起来，通常不够。

### 4.2 用软件工程解决 Agent 的问题（SE for Agent / Agentware）

这条路线把 LLM Agent 当作被开发和维护的软件：测试对象包括模型调用、工具接口、提示词、上下文和多步执行流程。相比单一代码生成任务，这类方法和评价标准仍在形成；“更新”不表示已有统一可靠的工程方案。

| 问题 | 可形成的研究问题 |
|---|---|
| 可观测性 | 怎样把自然语言思考、工具调用、环境状态和最终结果连起来，使人能够查询“哪一步导致了后面的失败”？ |
| 测试 | Agent 的单元测试、集成测试、回归测试应怎样定义？在没有唯一标准答案时，能否用变形测试——改变输入后检查输出是否仍满足应有关系——来发现错误？ |
| 调试 | 失败来自模型、提示词、记忆、检索、工具、环境还是多个部件之间的调度？能否自动定位？ |
| 可复现性 | 固定或记录模型版本、工具、依赖和输入后，怎样重放任务并比较每一步的动作与结果？ |
| 安全 | 怎样限制命令、权限、数据访问和不安全代码，同时保留任务完成能力？ |
| 维护与演化 | 模型、工具的输入输出格式、依赖和提示词升级后，怎样发现原来能完成的任务现在失败了？ |
| 性能与成本 | 在满足任务成功率的条件下，怎样减少 token 消耗、等待时间、工具运行和人工接管成本？ |
| 人机协作 | Agent 何时应该询问、解释、请求审批、交还控制或拒绝行动？ |

这些工作分别检查输入归因、执行轨迹和框架缺陷，提供了不同的诊断证据。例如，可以关联 Agent 读取的文件、当时的工具返回和后续补丁，检查错误信息是否影响了修改；但要证明某一步导致失败，还需要干预、重放或其他对照，不能只凭一段看似合理的解释。

## 5. 哪些方向成熟、拥挤或正在冒头

### 5.1 已成熟，但仍有长期价值

- **测试、模糊测试、静态/动态分析、程序修复。** 相关工具与对照方法已很丰富，但跨语言、并发、分布式程序，以及 LLM 应用和 Agent 仍不断产生新的分析与验证问题。新工作需要说明现有方法遗漏了什么条件，而不只是更换底座模型。
- **软件仓库挖掘和实证研究。** 这类研究从代码提交、问题单和代码评审等历史数据中寻找规律。方法已成熟，单纯统计 GitHub 数据很难创新；但新的开发形态、Agent 协作、AI 生成代码合并请求、供应链和组织治理提供了新现象。
- **软件维护、依赖和 API 演化。** 不时髦但稳定重要。若结合自动迁移、生成代码使用过期 API、依赖风险或真实企业环境，仍有空间。
- **开发者研究。** 它研究工具对人的理解、效率、协作和责任有什么影响。简单问卷已经拥挤，但长期部署、真实使用行为、团队级生产力、认知负担和责任分配仍然稀缺。

### 5.2 已明显拥挤，低配版本正在过时

- 只在 HumanEval、MBPP 等函数级代码生成评测，或 Defects4J 等 Java 缺陷集上比较几个 LLM 的通过率，没有检查真实使用条件；
- 只靠调整提示词提高单一任务分数，没有真实执行、有竞争力的对照方法或原因解释；
- 把多个角色提示词串起来就称为多 Agent，却不与单 Agent 或固定流程比较，也不通过消融检查各角色的作用；
- 用 LLM 做分类、摘要、情感分析或缺陷定位，再与很旧的机器学习方法比较；
- 只报告成功率，不报告成本、方差、失败类型、数据污染、模型版本和可复现性；
- 在很小的开源项目集合上展示工具可行性，却没有说明这些项目是否有代表性、结论换到其他项目是否仍然成立。

这些题目不是绝对不能做，而是需要加入新的研究对象或证据。例如，把“LLM 生成测试”改成“在长期变化的大型仓库中，怎样持续维护 Agent 生成的测试，避免测试的正确性判据因无关变化而频繁失效”，研究价值会完全不同。

### 5.3 正在增长，值得重点关注

1. **Agent 可靠性工程**：对多步软件修改或工具操作记录执行过程、定位失败、检查版本升级后的旧任务是否退化，并评测重试或恢复策略。
2. **程序分析、测试、形式方法与 Agent 的混合**：用调用图缩小修改范围、用测试检查补丁、用逻辑规则限制操作，并检验证据缺失或不准确时是否仍然有效。
3. **评测科学**：排除模型见过题目的影响，按时间更新题目，保留真实依赖，多次运行，并研究质量和成本之间的最佳折中以及评测集怎样长期维护。
4. **仓库级和长期任务**：跨文件修改、依赖升级、迁移、集成测试，以及从问题单到代码合并请求的完整链条。
5. **Agent 软件供应链**：研究模型、提示词、工具、插件、记忆库和第三方数据的升级与攻击风险；MCP（Model Context Protocol）是连接模型应用与外部工具、数据的协议，不代表这些部件已经安全可信。
6. **AgentOps / AIOps**：前者管理 Agent 的部署、运行和质量，后者用 AI 辅助 IT 运维。两者在生产故障分诊等场景中交叉，但监控 Agent 与让 Agent 处理线上系统是两个不同对象。
7. **人—Agent 团队**：何时询问、何时接管、怎样建立信任、怎样衡量团队而非单人的生产力。
8. **规格驱动与意图中心开发**：先清楚表达“想实现什么、必须遵守什么、怎样算完成”，再让 Agent 写代码，而不是把现有代码本身当作唯一事实。

### 5.4 本报告代表证据较少的方向

- Agent 能耗和环境成本；
- 量子软件工程，即研究量子程序怎样开发、测试和维护；
- 完全自治的软件组织或“多 Agent 软件公司”；
- 自动从组织过程记录生成 Agent；
- 面向特定行业法规的长期 Agent 工程。

这些条目是需要继续查证的观察方向，不表示相关领域整体都处于早期；例如量子软件工程已有持续研究，本报告只是没有系统覆盖其论文。仅凭名称新颖，不能判断研究机会大小。

## 6. 一组足够理解趋势的代表论文

不需要全部精读。建议先读“问题和结论”，再决定是否进入方法细节。

| 年份 | 工作 | 它做了什么 | 对领域发展的实际启示 |
|---|---|---|---|
| 2024 | [开发者调查](evidence/representative-papers.md#assistant-usability)（ICSE） | 调查 410 名开发者使用 AI 编程助手的动机、拒绝建议的原因和控制困难 | 需要观察人怎样验证和修改建议，不能只测生成准确率 |
| 2024 | [ClarifyGPT](evidence/representative-papers.md#clarifygpt)（FSE） | 在 LLM 按自然语言需求生成代码前识别歧义，向用户提问以补足需求 | 澄清什么信息、是否减少错误生成，都可以单独验证 |
| 2024 在线 / 2025 卷期 | [AutoSD](evidence/representative-papers.md#autosd)（EMSE） | 让修复 LLM 提出缺陷假设、执行调试命令，再依据返回结果生成解释和补丁 | 工具反馈可以支持修复和人工审查，但解释仍需要验证 |
| 2025 | [Unseen Horizons](evidence/representative-papers.md#unseen-horizons)（ICSE） | 改写代码生成评测的描述、代码和依赖上下文，用官方测试检查模型对陌生表述的表现 | 高分可能依赖熟悉的题目或表达；下降原因需进一步区分 |
| 2025 | [Agentless](evidence/representative-papers.md#agentless)（FSE / PACMSE） | 用固定的仓库缺陷定位、候选补丁生成和测试验证流程，与自主规划 Agent 比较 | 新增角色、记忆或反思机制应与简单流程比较成本和效果 |
| 2025 | [Agent 轨迹研究](evidence/representative-papers.md#agent-trajectories)（ASE） | 统一三种修复 Agent 的 120 条执行轨迹、2,822 次 LLM 交互，比较动作与反馈模式 | 分析中间过程能发现最终成功率掩盖的行为差异 |
| 2025 | [Watson](evidence/representative-papers.md#watson)（ASE） | 对 LLM Agent 的提示词输入做归因，辅助检查决策依据和定向修正 | 归因提供诊断线索，不等于直接读取真实内部推理 |
| 2025 | [Agent 框架缺陷研究](evidence/representative-papers.md#framework-bugs)（ASE Industry Showcase） | 从三个 LLM Agent 框架的 PR 中归纳 1,026 个缺陷的原因、症状与所在组件 | 框架代码和接口本身也需测试；该轨道不计入主研究标题统计 |
| 2025 | [Triangle](evidence/representative-papers.md#triangle)（ASE，经验论文） | 用多角色 LLM Agent 协商责任团队，处理真实云服务故障分诊 | 组织知识和交接时间是可验证的工程目标，不应扩大为全面自治运维 |
| 2026 | [修复系统横向分析](evidence/representative-papers.md#bug-fixing-analysis)（ICSE） | 在 SWE-bench Verified 上比较六种修复系统的定位、复现和修复表现 | 失败可能同时来自底座能力和执行流程，需要分开检查 |
| 2026 | [RefAgent](evidence/representative-papers.md#refagent)（ICSE） | 多角色 Agent 在八个 Java 项目上执行并验证重构，与单 Agent、搜索工具和人工历史比较 | 多角色是否必要，应由组件消融及代码质量检查支持 |
| 2026 | [SAINT](evidence/representative-papers.md#saint)（ICSE） | 从 Java 应用提取端点和调用顺序约束，让 Agent 生成接口与业务场景测试 | 代码分析结果能提供测试规划依据，但仍需检验覆盖与缺陷发现能力 |
| 2026 | [thea](evidence/representative-papers.md#secure-executions)（ICSE） | 在 Llama 3.1 推理时干预与漏洞有关的内部表示，用 CyberSecEval 检验生成代码安全性 | 对象是代码生成模型的执行，不是多 Agent 工作流 |
| 2026 | [商业 LLM 研究复现分析](evidence/representative-papers.md#commercial-llm-reproducibility)（ICSE） | 调查 86 项研究，并检查 18 项使用 OpenAI 模型、提供实验材料的研究能否复现 | 模型可用性、依赖、数据和脚本条件决定研究能否被重新检验 |
| 2025 | [2030 软工路线图](evidence/representative-papers.md#roadmap-2030)（TOSEM） | 从 AI、人因、可持续、自动编程、安全、验证和量子七类问题组织研究议程 | 提供领域视角；路线图不是对每个方向成熟度的实验验证 |

## 7. 各方向目前做到了什么程度

下面的“成熟度”不是给方向排高低，而是描述证据积累到了哪一步：**相对成熟**表示已有稳定问题定义和大量对照方法；**快速推进**表示已经能完成一部分真实任务，但能力边界仍明显；**早期**表示已有原型或现象研究，还没有公认的方法和评价标准。

| 方向              | 目前已经做到                                 | 仍然做不到或不稳定                                    | 阶段判断                      |
| --------------- | -------------------------------------- | -------------------------------------------- | ------------------------- |
| 传统测试与程序分析       | 已形成覆盖率分析、静态检查、模糊测试、故障定位和自动修复等成熟工具与研究方法 | 大型系统、并发与分布式程序、跨语言代码仍难分析；误报、漏报和运行成本长期存在       | 领域基本盘成熟，但问题远未结束           |
| 软件安全与供应链        | 能扫描已知漏洞和危险依赖、分析恶意软件包，并对部分漏洞生成修复建议      | 未知漏洞、复杂攻击链、依赖传播风险和自动修复的副作用仍难处理               | 方法较成熟，随云、开源依赖和生成代码持续演化    |
| 维护、依赖与 API 演化   | 已能从仓库历史发现维护规律，辅助重构、依赖升级和部分 API 迁移      | 跨多年版本的大规模迁移、隐含业务规则和组织特有知识仍高度依赖人              | 稳定而长期的研究方向，不是短期热点         |
| 需求、架构与开发者研究     | 已有需求追踪、架构分析、用户实验和开发者行为研究等完整方法体系        | 需求含糊、架构决策的长期影响、团队生产力和责任分配难以用单一指标衡量           | 成熟但证据获取困难，尤其缺少长期工业数据      |
| AI 编程助手         | 能补全常见代码、解释局部逻辑、生成简单测试和文档；开发者已经真实使用     | 容易误解隐含需求，生成结果仍需人检查；团队长期生产力提升没有简单统一的结论        | 工具已普及，研究问题转向可控性和人机协作      |
| 仓库级缺陷修复 Agent   | 能读问题单、搜索仓库、修改多个文件并运行测试；在部分标准评测题上已有较强结果 | 对环境搭建、依赖、跨服务故障、含糊需求和长时间任务仍很脆弱；同一任务多次运行结果可能不同 | 快速推进，但离稳定替代开发者还有明显距离      |
| 测试生成与自动调试       | 能生成单元测试、提出调试假设，并利用运行结果继续修改；程序分析可帮助缩小范围 | “测试通过”不一定代表需求正确；测试随代码演化后的维护、复杂系统复现和正确性判定仍难   | 传统方法成熟，LLM/Agent 增强部分仍在推进 |
| 程序分析与 Agent 混合  | 已有工作把调用关系、接口、覆盖率等事实交给 Agent，减少纯文字猜测    | 证据如何选择、错误证据怎样影响 Agent、能否跨语言和大型系统稳定工作尚不清楚     | 已出现可信原型，尚未形成通用方案          |
| Agent 可观测性与调试   | 已能记录“思考—动作—结果”轨迹，并初步归纳成功和失败模式          | 缺少统一记录格式、可靠的失败根因定位和跨框架比较；很难证明某一步就是失败原因       | 早期，但增长很快                  |
| Agent 框架与供应链可靠性 | 已经发现并分类了编排框架、工具和版本变化带来的真实缺陷            | 模型、提示词、插件、权限和第三方数据共同变化时，仍缺少系统测试和兼容性保障        | 早期，问题已被确认，工程方法尚未定型        |
| 生产运维 Agent      | 在故障分诊、日志归纳、知识检索和操作建议等限定任务上已有工业案例       | 自动改配置、执行恢复等高风险操作仍需要严格审批；组织知识会过时，生产数据也难公开复现   | 局部场景可用，全面自治仍不现实           |
| 人—Agent 协作      | 已有调查和实验研究何时接受建议、怎样澄清需求、如何让人保持控制        | 缺少长期团队研究；责任如何分配、过度依赖怎样避免、效率收益如何衡量仍无定论        | 问题重要，长期证据不足               |
| 评测与复现           | 社区已经意识到数据污染、模型更新、随机性、成本和环境差异会扭曲结果      | 仍缺少能长期更新、接近生产、成本可控且不同研究都能复现的统一评测体系           | 从“只看排行榜”转向研究评测本身          |

### 7.1 一个总体能力判断

当前技术已经越过了“只能生成一个孤立函数”的阶段，开始能够处理真实仓库中的多步任务；但它还没有越过“稳定的软件工程自动化”这条线。现有强结果通常依赖边界清楚的问题、可运行的测试、准备好的环境和有限的操作权限。一旦任务涉及含糊需求、多个服务、长期演化、生产风险或组织责任，人的判断仍然不可替代。

因此，论文中出现“达到很高成功率”时，需要继续追问：是在什么评测集上？环境是否预先准备好？允许尝试多少次？失败任务是否被排除？成本是多少？这些条件决定了结果距离真实使用还有多远。

## 8. 最新前沿：下一步主要在研究什么

下面把正在形成的前沿主线展开。每条主线都来自上一节尚未解决的能力缺口。

### 8.1 Agent 失败轨迹的可观测、分类与自动诊断

**它在做什么：** 给 Agent 装上类似“行车记录仪”的能力，保存它读了什么、调用了什么工具、看到什么结果，再自动找出失败发生在哪一步。

**核心问题：** 当 Agent 在长任务中失败，怎样判断是需求理解、上下文选择、工具调用、环境状态、结果判定标准还是模型推理导致？

**为什么成为前沿：** Watson 和轨迹研究提供了成功率之外的输入归因与行为证据，但两者并不等价：前者推断输入影响，后者检查实际动作和反馈。跨框架比较、失败根因确认，以及升级后旧任务的回归检查仍需进一步研究。

**目前做到哪一步：** 已能收集工具调用和模型输出、统一部分框架的日志并人工标注失败类型；让更多框架记录可比较的状态和动作、自动确认根因，再选择恢复步骤，仍需进一步验证。

**观察重点：** 下一阶段是否会形成类似传统分布式追踪的统一标准，以及诊断结果能否真正提高恢复成功率，而不只是把日志展示得更漂亮。

### 8.2 程序分析或运行时证据增强的 Agent

**它在做什么：** 把调用关系、测试覆盖、日志或性能数据交给软件修复、测试或调优 Agent，帮助它确定检查范围。例如，若性能采样显示大部分时间耗在某条调用链上，可以让 Agent 优先检查该链；这是方法示例，不是本文报告的测量结果。

**核心问题：** 哪些不运行程序即可得到的代码证据，或运行程序后收集的行为证据，能真正缩小 Agent 的查找范围并减少错误修改？

**为什么成为前沿：** 只读代码文本容易遗漏调用和状态关系，程序分析则能提供覆盖范围有限、假设可检查的证据。SAINT 展示了这种组合；另一类可用方法是差分测试，即让多个实现处理同一输入并比较结果差异，但差异本身还需正确性依据来判断哪一方有错。

**常用证据：** 函数调用图、测试覆盖率、数据在程序中的流动路径、性能采样、日志中的因果链、硬件或系统性能计数器、依赖图、与失败最相关的代码片段。

**目前做到哪一步：** 已有工作证明调用关系、服务接口、测试结果等证据能够帮助特定任务；尚未解决的是如何自动选择最有用的证据、怎样处理互相矛盾或已经过时的证据，以及能否推广到大型、多语言系统。

### 8.3 面向 Agent 的性能与成本工程

**它在做什么：** 把 Agent 当作一个会消耗模型调用、计算、时间和人工注意力的系统，研究怎样用更少资源稳定完成任务，而不只是追求一次测试的最高成功率。

**核心问题：** Agent 处理的文字量、响应延迟、工具调用、运行环境启动、失败重试和人工接管怎样共同决定任务成本？能否在保证一定成功率的前提下优化？

**为什么成为前沿：** 当前 Agent 论文常报告成功率，却缺少覆盖“收到任务—完成任务”全过程的资源模型。一个方法即使更准确，如果需要几十倍模型调用或频繁人工接管，也未必能实际部署。

**可探索的具体决策：** 为同一软件任务选择底座 LLM、并发 Agent 数、重试次数和上下文保留策略；分别记录模型推理、工具执行和人工接管的消耗。跨 CPU/GPU/NPU 部署还需区分模型服务的硬件成本与 Agent 流程本身的成本，这是进一步研究的问题，不能视作所列代表论文已经完成的成果。

**目前做到哪一步：** 研究通常已经会报告模型调用量和时间，但不同任务的计算、工具和人工成本仍难统一比较；在成功率约束下自动选择模型、并发数和工具策略，仍属于较新的问题。

### 8.4 Agent 框架、插件和工具供应链可靠性

**它在做什么：** 研究 Agent 所依赖的一长串部件在升级或被攻击时会发生什么。它类似传统的软件供应链安全，只是依赖项还多了模型、提示词、工具接口和记忆数据。

**核心问题：** 当模型版本、提示词、MCP 工具的参数或返回格式、插件和依赖升级时，原来成功的任务是否会失败、调用错误工具或越过权限边界？怎样通过回归任务和接口检查提前发现？

**为什么成为前沿：** Agent 的行为不只由模型决定，还受到提示词、工具、插件、权限和外部数据共同影响。已有 Agent 框架缺陷研究给出了起点，但工具生态、版本兼容和多个部件互相影响的故障仍快速变化。

**目前做到哪一步：** 社区已经从真实问题单和代码合并请求中确认了这类缺陷，但针对模型或工具升级的兼容性测试、权限分析和自动迁移方法还没有形成成熟体系。

### 8.5 生产运维中的可控 Agent

**它在做什么：** 让 Agent 帮助处理线上告警和故障，但不盲目追求完全自动化；重点是明确哪些操作可以自动执行，哪些必须先请人确认。

**核心问题：** Agent 在生产故障分诊、根因分析、配置变更或容量管理中，何时可以自动行动，何时必须询问或交给人？

**为什么成为前沿：** 生产运维有清晰业务指标和真实反馈，也最直接暴露 Agent 的权限与责任问题。Triangle 展示了故障分诊的工业价值，但安全边界、知识变化、跨团队协作，以及系统长期变化后方法是否仍有效，仍是开放问题。

**目前做到哪一步：** 日志归纳、故障分诊和操作建议已经可以在限定场景中提供帮助；直接修改生产配置或自主恢复仍受到风险限制。公开研究也常因拿不到真实生产数据而只能使用故障报告、Kubernetes 故障注入或测试环境。

### 8.6 规格驱动的人—Agent 协作

**它在做什么：** 让 Agent 在写代码前先确认“用户到底想要什么”和“怎样才算完成”，遇到歧义时主动询问，而不是错误地猜出一个看似合理的需求。

**核心问题：** 怎样让 Agent 在修改代码前主动识别含糊需求、生成可执行接受条件，并在不确定时请求人类决策？

**为什么成为前沿：** 当前大量失败不是模型不会写代码，而是需求、上下文和“怎样算完成”没有说清楚。因此，研究重点开始从提高生成率转向让 Agent 主动澄清、解释不确定性并请求人类决策。

**目前做到哪一步：** 已有方法能够提出澄清问题、生成接受条件或在高风险操作前请求批准；它们是否真的减少返工、怎样避免过度打断开发者，以及责任怎样划分，仍需要长期用户研究。

## 9. 怎样理解这些方向为什么会变化

把近三年的论文放在一起看，可以看到研究重心沿着几条轴同时移动：

| 观察角度 | 较早或较简单的研究 | 当前主流 | 正在形成的前沿 |
|---|---|---|---|
| 任务范围 | 生成一个函数或一次回答 | 修改真实仓库、调用工具、运行测试 | 跨服务、长时间、持续演化和生产环境任务 |
| AI 的角色 | 提供一次建议的助手 | 能连续行动的 Agent | 需要被测试、监控、约束和治理的软件部件 |
| 评价目标 | 单次准确率或测试通过率 | 完整任务成功率、成本和重复运行 | 长期可靠性、可诊断性、安全、责任和组织影响 |
| 使用的证据 | 固定数据集和代码文本 | 可执行仓库、测试和工具反馈 | 运行时数据、组织知识、真实用户和长期部署 |
| 人的角色 | 给数据、看最终结果 | 审查修改、提供上下文 | 在关键节点审批、纠正目标并承担责任 |

### 9.1 为什么有些方向快速变热

一个方向通常不是因为名称新就成为前沿，而是三个条件同时出现：新技术让过去做不到的任务变得部分可行；真实使用暴露了新的失败；社区又获得了可以研究这些失败的数据。例如，Agent 能够连续调用工具之后，才会出现长轨迹调试、工具权限、上下文维护和成本控制这些新问题。

反过来，一个方向变得拥挤，通常是因为问题已经被简化成固定数据集上的分数竞争，而新的论文没有带来新现象、新方法或更真实的证据。这正是“换一个模型重新跑旧题”价值下降的原因。

### 9.2 当前方向选择背后的共同标准

从社区整体看，较受重视的方向通常满足至少一项：能进入过去无法处理的真实任务；能解释现有方法为什么失败；能提供新的公开数据或评测；能建立可复现、可比较的方法；或者能证明工具确实改变了开发和运维过程。这里的“方向选择”本质上是在选择一个尚未解决、同时又能获得可信证据的问题，而不是选择一个最流行的技术名词。

### 9.3 最短阅读路径

如果只想快速建立全局认识，可以依次读：第 2 节的领域地图、第 3 节的三年变化、第 7 节的能力边界、第 8 节的最新前沿。第 4–6 节用于补充两条 Agent 路线、成熟度判断和代表论文；其余方法与来源可在需要核查时再看。

## 10. 怎样从现成工作里挖出软工论文：几个关键转念

**核心逻辑：已有工程 → 反复出现、现有方法解释或解决不好的问题 → 别人也能使用的认识或方法 → 可核验的证据。** “包装”最有价值的部分，是找准工作实际支持的研究主张，并补上验证它的证据。

**① 最值得挖的，往往是让你反复返工的地方。** 为适配不同环境写的补丁、人工排错、失败重试、升级兼容，可能比系统的主功能更有研究价值：它们暴露了现有方法遗漏的条件。先找“为什么每次都卡在这里”。

**② 把项目名拿掉，看看还剩下什么问题。** “我做了一个部署平台”描述的是成果；“怎样在依赖不断变化时重建可复现的故障环境”才是其他项目也可能面对的问题。这一步决定工作能否从项目经验变成可推广的知识。

**③ 你积累的历史，可能比新写的算法更有价值。** 失败日志、修复记录、人工决策和版本变化，可以支撑实证研究：某类失败有多普遍、为什么发生、现有方法漏掉了什么。只有分类清单还不够，还要说明它改变了什么认识或工程决策。

下面是转化思路示例，并不意味着这些题目已经具有新颖性：

| 现成工作 | 可以挖出的研究问题 | 最关键的补证据 |
|---|---|---|
| 多次排障、搭建测试环境 | 工具失败究竟来自算法，还是环境无法复现？ | 保存失败现场，在相同任务上比较环境修正前后 |
| 依赖升级、API 适配和迁移脚本 | 哪些兼容性问题可以提前发现或自动修复？ | 跨版本实例、已有迁移工具对照、修复后的功能验证 |
| 调度或性能优化 | 哪些运行证据能帮助开发者更快定位性能退化？ | 定位准确率、排查时间、不同项目验证；吞吐量提升本身主要是系统贡献 |
| Agent 工作流与工具集成 | 哪些步骤真正提高成功率，哪些只是增加成本？ | 固定任务和模型，逐项移除组件，多次运行比较 |
| 多次人工审查与接管 | 人通常在什么节点补上了自动化缺失的信息？ | 接管前后记录、统一标注、验证哪些介入确实有效 |

**④ 最小研究单位可以是一个关键机制。** 不必把整个系统都写进论文。抽出一个模块，回答“为什么它有效、去掉它会怎样、换个环境还有效吗”，往往更容易形成清楚的贡献。

**⑤ 最后用一句话验收：** “我们在【场景】发现【反复出现的问题】，现有方法因为【遗漏的条件】处理不好；我们用【数据或方法】得到【新认识或改进】，并在【范围与对照】下验证。” 填不出的部分，就是需要补的研究。尤其检查两点：已有论文是否已经回答过，以及结果是否只是某个项目的偶然现象。

## 11. 最终判断

软件工程的基本盘仍然是测试、分析、安全、维护、开发者与组织等长期问题；LLM 和 Agent 没有取代这些方向，而是把它们带入了新的对象和场景。

近三年的核心变化可以压缩成一句话：

> **研究已经从“模型能否生成代码”，走到“Agent 能否在真实仓库中连续完成任务”，又进一步走向“怎样把 Agent 本身做成可测试、可观察、可约束、可维护的软件系统”。**

目前最前沿的工作大多位于这条边界上：一方面利用程序分析、测试和运行数据提高 Agent 的可靠性；另一方面研究评测、成本、安全、人与组织，使局部演示逐渐接近可长期使用的工程系统。现阶段已经能看到大量有用原型和部分工业落地，但距离通用、稳定、低成本、可承担责任的自动化软件工程仍然很远。
